# TASK_20260412_033.md

## 本轮目标
本轮只完成：在已经有内存版 request log store 的后端写作链路上，把请求日志整理成一个**可查询的内存读模型**，让后续后台查询接口和管理页可以直接复用，而不需要先上数据库。

---

## 本轮背景

- `task/TASK_20260411_027.md` 已经把 `Backend/` Swift + Vapor 骨架、`GET /v3/health`、`POST /v3/client/bootstrap` 和内存态 `deviceToken` 复用跑通。
- `task/TASK_20260411_028.md` 已经把 `POST /v3/writes/start` 跑通，并验证了 bootstrap-issued token 的校验、backend-only transport envelope 和 deterministic stub completion。
- `task/TASK_20260412_029.md` 已经把写作 transport envelope 做成 route-neutral，并把 `POST /v3/writes/continue` 接到了同一条 bootstrap-token 路径上。
- `task/TASK_20260412_030.md` 已经把 `POST /v3/writes/edit` 接到了同一条 bootstrap-token 路径上，并补了选区校验。
- `task/TASK_20260412_031.md` 已经把三条写作路由共用的内存版 quota gate 跑通了，日 / 周限额按 `installationId` 记账，拒绝请求不计数。
- `task/TASK_20260412_032.md` 已经把三条写作路由的请求元数据统一记到了内存版 request log store 里。
- 现在 backend 里已经有了日志数据，但还没有针对后台查询需要的过滤、排序、统计能力。
- 这一张 task 只负责**日志查询读模型**，不做数据库、Redis、admin UI 或 HTTP admin 路由。

## 本轮要做

- 在 `Backend/` 里把现有内存 request log store 扩展成可查询读模型
- 提供足够后续后台查询接口直接复用的查询能力
- 查询维度至少支持：
  - `installationId`
  - `action`
  - `status`
  - `errorCode`
  - `createdAt` 时间范围
- 保留现有日志条目的只读快照接口，不破坏已经通过的日志写入行为
- 提供一个轻量的聚合摘要，至少能按查询结果计算：
  - 总请求数
  - accepted 数
  - rejected 数
- 查询结果按时间倒序返回，方便后续接后台列表页
- 继续保持内存实现，不引入数据库或持久化
- 补最小测试，覆盖：
  - 按 installationId 过滤
  - 按 action / status 过滤
  - 按 errorCode 过滤
  - 按时间范围过滤
  - 聚合摘要统计正确

---

## 建议实现内容

以下不是唯一实现方式，但请保持目标一致：

- `Backend/Sources/VibeWriteBackend/Services/InMemoryRequestLogStore.swift`
- `Backend/Tests/VibeWriteBackendTests/RequestLogQueryTests.swift`
- 以 `RequestLogQuery` / `RequestLogFilter` 之类的轻量结构表达查询条件
- 查询实现应尽量直接复用当前 `snapshot()`，不要把日志存储和查询拆成两套逻辑
- 结果排序默认按 `createdAt` 倒序
- 聚合摘要先做最小值集，不要提前设计复杂分组 / 分页 / 导出
- 查询结果和摘要都不要包含正文、摘要、`project.prompt`、`userMessage`、`selectionText` 或 AI system prompt 原文
