# TASK_20260402_013.md

## 本轮目标
本轮进入 V2-M2：把 VibeWrite 的主路径真正收束成 `startDraft -> continueWriting -> edit`，让用户在正常 runtime 里能够顺手地起稿、续写、局部编辑，而不是被一堆附加语义分散注意力。

这轮的重点不是再扩入口，而是把现有正文优先骨架上的动作模型讲清楚、跑顺：

- `startDraft` 负责从首页直接起稿
- `continueWriting` 负责在已有正文基础上继续往下写
- `edit` 负责对选区或局部意图做修改

当前 UI 已经收束到 V2-M1 的页面骨架，但动作层还没有完全按 V2-M2 收口，尤其是：

- 会话页里还有一些辅助动作名称和建议 chips 没有完全统一到三动作主线
- 正常交互中，续写和编辑的触发语义还不够直观
- `expand / shorten / polish` 这类表达更像内部 edit 细分，不应该继续占据主路径的可见位置

这轮的判断标准不是“能不能触发一个 AI 请求”，而是“用户是否能在正文中心页面里自然地理解三种动作各自该在什么时候发生”。

## 本轮背景

- task011 已经完成 V2-M1 的编辑器优先骨架。
- task012 已经清掉首页残留的 V1 讨论式 runtime 语义。
- 现在的页面结构方向是对的，但动作模型还需要继续收束，和 `docs/V2/PRD2.0.md`、`docs/V2/IA2.0.md`、`docs/V2/AGENTS.md` 里的三动作主线完全对齐。

### 这轮要统一的判断
- 用户在首页起稿后，下一步是否自然就是继续写或编辑
- 选中文本后，用户是否能明确地走进局部编辑路径
- 页面上的文案和按钮是否仍在暗示过多细分动作
- 代码里的动作分流是否仍依赖过多语义分类，而不是状态 + UI 结构

## 本轮要做

- 收口三动作主路径
  - 首页保持 `startDraft`
  - 已有正文时，主协作入口要明确服务 `continueWriting`
  - 选区或局部意图要明确服务 `edit`
  - 不要再让 `expand / shorten / polish` 以主入口的形式出现在正常 runtime 里

- 统一会话页的动作语义
  - 会话页里的主按钮、提示文案、chips 和选择浮层要围绕三动作来设计
  - 如果 `expand / shorten / polish` 仍然存在，只能作为 `edit` 的内部实现细节或轻量文案，不要继续作为独立主动作展示
  - 续写和编辑的入口应该比现在更直观，避免用户还得猜该点哪个按钮

- 收紧动作路由
  - 不要继续依赖复杂关键词分类去决定主路径
  - 让当前状态、正文是否存在、是否有选区，决定用户更像是在 `continueWriting` 还是 `edit`
  - 起稿、续写、编辑都要尽量短，响应契约仍然保持轻量

- 保持正文中心
  - 不改首页骨架
  - 不改写作页的大结构
  - 不把页面做回工作台
  - 继续让正文是主视觉，动作只是服务正文的入口

- 真实验证页面效果
  - 改完后必须实际启动 app，验证首页起稿、会话页续写、选区编辑都能自然触发
  - 不能只跑单测
  - 要确认正常 runtime 的主路径真的变成三动作主线，而不是表面上换了名字

1. 先阅读 `docs/V2/PRD2.0.md`、`docs/V2/IA2.0.md`、`docs/V2/UI2.0.md`、`docs/V2/Wireframes2.0.md`、`docs/V2/AGENTS.md`、`docs/V2/Milestones.md`，确认这一轮必须围绕三动作主线收口。
2. 复述当前代码里 `startDraft`、`continueWriting`、`edit` 的实际触发路径，找出哪些是主路径，哪些只是内部细分或兼容动作。
3. 收紧首页和会话页的动作入口，让用户在当前状态下更自然地走到对应动作。
4. 清理或弱化那些仍然显性暴露的细分动作名称，让它们回到 `edit` 的实现细节里。
5. 更新 unit test / UI test，明确覆盖三动作主路径。
6. 跑 `swift test` 和 `xcodebuild test -project VibeWrite.xcodeproj -scheme VibeWrite -destination 'platform=macOS'`。
7. 实际启动 app，确认首页起稿、会话页续写、选区编辑这三件事都能在正常 runtime 里顺手完成。
