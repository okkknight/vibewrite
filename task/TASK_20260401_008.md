# TASK.md

## 本轮目标
本轮只完成一件事：修复 VibeWrite 启动后出现 `invalid api key (2049)` 的根因，确保开发机启动时不会因为错误的 MiniMax 配置来源而直接暴露服务端拒绝错误。

这不是一个 UI 文案修复，也不是单纯把错误隐藏掉。本轮要把 AI 配置读取、运行时 client 选择、以及无效 key 的降级行为一起理顺，让 app 在下面两种情况下都表现正确：

1. 配置可用时，正常进入真实 AI 流程。
2. 配置不可用或 key 无效时，明确降级，而不是把服务端 `2049` 错误直接抛到用户界面上。

---

## 本轮背景

- 当前 app 启动后会走真实 AI 路径。
- 用户在首页起稿后，正文区直接出现 `invalid api key (2049)`。
- 我已经确认过：
  - 运行中的 shell 里带着 `MINIMAX_API_KEY`
  - app 的 AI 配置优先读进程环境变量
  - 当前构建出来的 app bundle 里并没有把 `MINIMAX_API_KEY` 和相关 AI 配置键真正写进去
- 这意味着当前问题很可能是“配置来源不一致 + 无效 key 未被正确降级”，而不是单纯的前端提示问题。

### 需要优先定位的点
- app 到底是从哪里拿到这把 key 的
- `Info.plist` / `xcconfig` / `ProcessInfo.environment` 三层的优先级是否合理
- 当前配置缺失时是否应该自动退回 stub / missing-config 状态
- 当前无效 key 时是否应该展示更明确、可操作的错误，而不是直接显示服务端 `2049`

---

## 本轮要做

- 梳理并修正 AI 配置读取链路
  - 明确 `WritingAIConfiguration.current()` 的数据来源和优先级
  - 不要让开发者 shell 里残留的 `MINIMAX_API_KEY` 误伤正常启动
  - 不要让 bundle 没配置、环境里有旧 key 的情况默默走到真实请求

- 修正 app bundle 配置注入方式
  - 确认 `VibeWrite.xcconfig`、`VibeWrite.local.xcconfig`、`Config/VibeWriteInfo.plist` 的组合方式是否真的把 AI 配置带进 app bundle
  - 如果当前 `INFOPLIST_KEY_*` 在这个工程结构里不会生效，就改成实际可生效的方案
  - 目标是让运行时读取到的配置来源稳定、可预期、可维护

- 明确 real / stub 的切换规则
  - 如果没有有效的 MiniMax key，就不要创建真实 client
  - 如果只有格式上存在但服务端不接受的 key，不要把错误直接打到正文区
  - 至少要给出一个清晰的“缺少配置 / 配置无效 / 服务不可用”状态

- 修正错误处理体验
  - 不要在页面上直接裸露 `invalid api key (2049)` 这种服务端原始错误，除非这是唯一可操作的信息
  - 如果需要保留错误，也要改成更明确的产品级提示
  - 失败态下，用户已有输入和当前编辑状态不要被破坏

- 补充最小测试
  - 覆盖“无环境变量时不应误读旧 key”
  - 覆盖“bundle / env 组合下的配置优先级”
  - 覆盖“无有效 key 时应回退到 stub 或 missing-config 状态”
  - 覆盖“真实 API 错误不会被当成未处理的 UI 崩溃”

## 本轮主流程

1. 先复述当前 `invalid api key (2049)` 的实际链路，确认是读取了哪一层配置。
2. 盘点 `WritingAIConfiguration`、`WritingAIClientFactory`、app 启动路径和工程配置文件的关系。
3. 明确 `real` 与 `stub` 的切换策略，决定配置缺失时的默认行为。
4. 修正工程配置，让 app bundle 里的配置来源和运行时读取方式一致。
5. 必要时调整错误映射，让无效 key 的提示更符合产品预期。
6. 补最小测试，覆盖配置优先级和降级路径。
7. 运行 `swift test` 和 `xcodebuild test -project VibeWrite.xcodeproj -scheme VibeWrite -destination 'platform=macOS'` 确认没有回归。

## 建议的实现内容

以下不是唯一实现方式，但请保持目标一致：

- `Sources/VibeWriteApp/Shared/AI/WritingAIConfiguration.swift`
  - 重新审视 `ProcessInfo.environment` 与 bundle config 的优先级
  - 不要让外部 shell 环境里的旧 key 无意识覆盖项目配置
  - 为“配置缺失 / 配置无效 / 真实模式可用”建立更清晰的判定

- `Sources/VibeWriteApp/Shared/AI/WritingAIModels.swift`
  - 让 `WritingAIClientError.missingConfiguration`、`requestFailed`、`invalidResponse` 的产品级文案更明确
  - 如果服务端返回的是可识别的配置错误，考虑做成单独的错误分支，而不是直接暴露 raw message

- `Sources/VibeWriteApp/Shared/AI/WritingAIConfiguration.swift`
  - `WritingAIClientFactory` 在 `shouldUseRealClient == false` 时继续回退 stub
  - 如果当前需要一个“显式缺少配置”的状态，也要保证 UI 不会误以为是系统崩溃

- `VibeWrite.xcodeproj/project.pbxproj`
  - 检查 app target 的 build settings 是否真的把 AI 配置写入正确位置
  - 如果 `Config/VibeWriteInfo.plist` 这个路径不会承载 `INFOPLIST_KEY_*`，就改成真正生效的方式

- `Tests/VibeWriteAppTests/`
  - 新增配置读取测试
  - 新增 client 选择测试
  - 如有必要，新增一个针对错误文案映射的测试
