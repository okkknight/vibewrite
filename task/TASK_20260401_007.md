# TASK.md

## 本轮目标
本轮只完成：把当前 VibeWrite 的实现重新对齐到 `docs/VibeWrite MVP PRD.md`、`docs/VibeWrite MVP IA.md` 和 `docs/VibeWrite MVP Wireframes.md`，重点修复四个用户可感知的偏差：

1. 首页两个起稿入口不能再把预置样板项目当成“起稿流程”本身，必须回到真实的起稿/讨论起稿入口语义。
2. 正文区的“选区修改”不能再用段落 rail 代替真实选区，必须让局部修改真正围绕正文中的选中文本展开。
3. 版本回退不能只停留在 `WritingProjectView` 的 view 本地状态，必须变成一个可用、可理解、可回退的线性历史机制。
4. 顶部“更多”菜单不能再出现空转按钮，至少要让文档里写到的本地级动作真正可用，或明确禁用尚未支持的动作，不要让用户点了没反应。

本轮目标不是重做 M1-M4 架构，也不是增加新功能，而是把现有体验修回到文档定义的最小闭环。

---

## 本轮背景

- 用户已经实际体验过当前版本，发现“能跑通”不等于“和文档一致”。
- 当前仓库里虽然已经有首页、项目页、AI 抽象层、本地存储和测试，但部分交互更像样板演示，而不是 PRD / IA / Wireframes 里描述的真实产品体验。
- 这轮要优先修复的是用户一眼就能感知到的偏差，而不是继续扩展能力。
- 相关参考文档：
  - `docs/VibeWrite MVP PRD.md`
  - `docs/VibeWrite MVP IA.md`
  - `docs/VibeWrite MVP Wireframes.md`

### 当前需要重点纠偏的地方
- 首页“直接起稿 / 先讨论再起稿”入口现在更像打开了预置项目，而不是进入真实起稿流程。
- 写作项目页的选区修改现在是用段落列表在冒充“选中正文”。
- 撤销 / 对比 / 本段重试现在主要依赖 view 内部临时状态，离“可靠的回退”还有差距。
- 顶部更多菜单里有看起来能点但实际上没有动作的项。

---

## 本轮要做

- 把首页两种起稿入口改成真正的起稿入口，不再把预置样板正文当作入口本身。
  - `createNewProject`
  - `direct start`
  - `discussion start`
  - `startQuickDraft`
- 让“直接起稿”和“先讨论再起稿”进入项目后呈现符合文档的初始状态。
  - 直接起稿：先进入一个新项目，再由 AI 生成第一稿
  - 先讨论再起稿：先进入讨论态，正文应保持空白或明确的讨论前占位状态，不要预先塞入成稿样板
- 把正文区的局部修改改成真正的“正文选区驱动”。
  - 用户在正文里选中的文本，必须能成为局部修改的来源
  - 现有的段落 rail 不能继续作为主来源
  - 如果纯 SwiftUI `TextEditor` 很难稳定拿到选区，允许替换正文编辑器为最小范围的 AppKit-backed 文本视图封装，但不要扩大成复杂编辑器重写
- 把版本回退改成一个小而可靠的线性历史。
  - 至少支持撤销、前后对比、本段重试三件事
  - 历史记录不能只活在 `WritingProjectView` 的临时状态里
  - 回退后正文、摘要、上下文和建议 chips 不能明显不一致
  - 不做复杂分支版本树，只做最小可理解的线性栈
- 把顶部“更多”菜单修成真正可用的本地动作。
  - `重命名` 要能改当前项目标题
  - `删除` 要能删除当前本地项目，并有明确确认
  - `导出（可后置）` 如果暂时不做，就不要做成假可点按钮；要么禁用，要么隐藏，要么给出明确的后置态，不要空转
- 为以上改动补齐或更新测试，保证行为可验证。

## 本轮主流程

1. 先对照 PRD / IA / Wireframes 复述这四个偏差各自为什么与文档不一致。
2. 盘点当前实现里相关代码路径，确认应该改哪些文件，避免重复造轮子。
3. 先修首页起稿入口和项目创建语义，去掉“预置样板 = 起稿入口”的错位。
4. 再修正文选区机制，确保局部修改来自真实正文选区而不是段落 rail。
5. 再把版本回退收敛成可靠的线性历史，保证 undo / compare / retry 的状态一致性。
6. 最后把顶部更多菜单接上真正动作，或者明确禁用暂不支持项。
7. 补测试并跑 `swift test` 与 `xcodebuild test`，确认这次改动没有把现有主流程弄坏。
