# TASK_20260420_048.md

## 本轮目标
本轮只完成：查清 `continueWriting` 偶发 `HTTP 413 Payload Too Large` 的真实触发层，解释为什么同一篇正文连续重试时会出现“前几次失败、后面又成功”，但不修改现有业务逻辑和用户体验。

---

## 本轮背景

- 目前已经能复现：用户在同一篇内容上连续点“继续写”，前几次可能返回 `HTTP 413 Payload Too Large`，但后面的某次又能成功。
- 现有 app 侧 request trace 已经记录到请求大小、字段拆分、响应状态和 `payloadFingerprint`，但单靠当前日志还不能解释“为什么同样的正文会时好时坏”。
- app 侧 trace 文件已经落盘在 `~/Library/Application Support/VibeWrite/diagnostics/backend-gateway-request-trace.log`，其中能看到同一轮 `continueWriting kind=prose` 请求在 `envelopeBytes=49990`、`projectBytes=49722`、`documentBytes=48042`、`userMessageBytes=9` 的情况下，先后出现过 `413` 和 `200`，说明问题不只是“请求一到某个固定大小就必死”。
- `userMessageBytes=9` 对应用户输入的 `继续写`，所以这批 trace 的成功 / 失败对比确实是在同一个动作路径上。
- 后端本地服务运行在 `127.0.0.1:8080`，当前 app 没有环境变量覆盖 backend base URL，说明这批请求走的是本机 backend gateway，不是远程服务。
- 现有后端日志里还没有稳定捕获到 `write request incoming` / `write request decoded`，所以失败点大概率在路由之前的 body 收集层，或者还有别的中间层差异需要确认。
- 已经核对到 `HTTP 413` 的直接报错源头和 Vapor 的请求 body 收集有关，具体落点在 `Backend/.build/checkouts/vapor/Sources/Vapor/Request/Request+BodyStream.swift`，说明这是后端 HTTP body 处理层抛出的 `Payload Too Large`，不是业务路由自己生成的错误。
- 我们还做过一次本机后端 body limit 的最小复现，发现 17KB 左右的 synthetic 请求会直接 `413`，这说明本机 backend 的 body 收集确实存在限制；但这和 trace 里同样 49,990 bytes 的请求有时成功、有时失败的现象仍然矛盾，所以还不能直接把结论收死。
- 这轮不是修复 413，而是把触发点、条件和差异查实，避免再靠猜测推进。

## 本轮要做

- 复现并对比同一篇正文在连续提交时的失败与成功请求。
- 直接确认 `HTTP 413` 是在什么层产生的：客户端、路由前 body 收集、路由进入后、还是别的中间层。
- 对比成功与失败请求的有效差异，至少要说明是哪个字段、哪个传输形态或哪个处理路径导致结果不同。
- 把调查结论写回 handoff / context，给后续修复留一份可靠的证据链。

---

## 本轮不要做

- 不改正文请求协议
- 不改 `continueWriting` 的产品语义
- 不改 UI 提示样式
- 不改 backend 的业务响应结构
- 不提前把结论收敛成“就是正文太长”或“就是固定 body limit”，除非证据已经闭死

---

## 本轮主流程
1. 先用现有 trace file 和后端日志把失败与成功请求按时间顺序对齐。
2. 确认失败请求到底有没有进入后端 route handler，还是在 route 之前就被 body 收集层拦下。
3. 如果现有日志还不够，补最小范围的定位日志，只加在最可疑的层，不扩散到无关模块。
4. 输出一份明确的排查结论，说明失败和成功请求的本质差异，以及下一步修复应落在哪一层。
