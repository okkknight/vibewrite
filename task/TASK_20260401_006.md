# TASK.md

## 本轮目标
本轮只修复 task005 review 里暴露的两个问题，确保真实 AI 接入链路在失败态和起稿态都更稳：
1. 协作态请求失败时，用户已输入的内容不要被清空，方便直接重试。
2. 起稿链路不要把同一个 prompt 重复塞进对话 / 请求上下文，避免 AI 输入和可见对话历史都出现重复用户回合。

---

## 本轮要做
- 修复协作态的失败恢复逻辑
  - `messageDraft` 只有在请求成功后再清空
  - 请求失败时保留输入内容和光标焦点
  - 已存在的错误提示仍然保留，方便用户修正后重试
- 修复起稿链路的 prompt 重复问题
  - 保证同一个 prompt 只进入一次请求上下文
  - 保证同一个 prompt 只出现在一次用户消息记录里
  - 直接起稿、先讨论再起稿两条链路都要一致
- 补充最小单测，覆盖：
  - 请求失败时输入内容保留
  - 起稿请求不会重复注入相同 prompt

---

## 本轮不要做
- 不重做 M4 的整体 AI 架构
- 不改真实 AI provider 的整体协议
- 不改 prompt builder 的大结构
- 不做额外功能扩展
- 不做新的 UI 页面
- 不做服务端或多模型路由

---

## 本轮主流程
1. 先复述这两个 review finding 的根因和修复边界
2. 设计最小修复方案，避免引入新的重复消息或失败态丢失
3. 修改 `WritingProjectView` 的提交流程，确保失败后输入仍在
4. 修改 `VibeWriteAppFlow` 的请求组装，确保起稿 prompt 不重复
5. 补充单测验证修复结果
6. 运行最小测试，确认 `swift test` 与 UI 流程不回归

---

## 建议的实现内容
以下不是唯一实现方式，但请保持目标一致：

- `WritingProjectView`
  - 在 async 请求成功后再清空 `messageDraft`
  - 请求失败时不清空输入框
  - 必要时保持/恢复焦点，减少重试摩擦
- `VibeWriteAppFlow`
  - 为起稿请求区分“已写入 conversation 的 prompt”与“仅用于模型请求的 prompt”
  - 避免 `performWritingAction(.startDraft, userMessage: ...)` 这条路径把 prompt 再 append 一次
  - 保持 discussion / collaboration 两条起稿流一致
- `Tests/VibeWriteAppTests`
  - 新增或调整测试，覆盖失败态输入保留
  - 新增或调整测试，覆盖 startDraft prompt 只注入一次
