# TASK_20260412_037.md

## 本轮目标
本轮只完成：在已经有 backend bootstrap、quota、request log、admin login、secret config store 和 system-prompt config store 的基础上，把 `POST /v3/writes/start`、`POST /v3/writes/continue`、`POST /v3/writes/edit` 从 stub 响应替换成**真实的后端 AI 执行路径**，让 backend 真正负责 prompt 组装、单模型调用和最终 `WritingAIResponse` 拼装。

---

## 本轮背景

- `task/TASK_20260411_027.md` 已经把 `Backend/` Swift + Vapor 骨架、`GET /v3/health`、`POST /v3/client/bootstrap` 和内存态 `deviceToken` 复用跑通。
- `task/TASK_20260411_028.md` 已经把 `POST /v3/writes/start` 跑通，并验证了 bootstrap-issued token 的校验、backend-only transport envelope 和 deterministic stub completion。
- `task/TASK_20260412_029.md` 已经把写作 transport envelope 做成 route-neutral，并把 `POST /v3/writes/continue` 接到了同一条 bootstrap-token 路径上。
- `task/TASK_20260412_030.md` 已经把 `POST /v3/writes/edit` 接到了同一条 bootstrap-token 路径上，并补了选区校验。
- `task/TASK_20260412_031.md` 已经把三条写作路由共用的内存版 quota gate 跑通了，日 / 周限额按 `installationId` 记账，拒绝请求不计数。
- `task/TASK_20260412_032.md` 已经把三条写作路由的请求元数据统一记到了内存版 request log store 里。
- `task/TASK_20260412_033.md` 已经把这个 request log store 整理成了可查询的内存读模型，支持过滤和摘要统计。
- `task/TASK_20260412_034.md` 已经把最小后台访问面跑通了，包含简单登录 / 登出和 `GET /v3/admin/requests`。
- `task/TASK_20260412_035.md` 已经把 `provider API key` 和 `admin 登录凭证` 收进同一份内存版 secret config store，后台登录和 `/v3/admin/secrets` 已经读同一份配置。
- `task/TASK_20260412_036.md` 已经把当前生效的 AI system prompt 配置搬进同一份内存版 system-prompt config store，后台可以通过 `GET/PUT /v3/admin/system-prompt` 查看和更新 current snapshot。
- 现在 backend 仍然在 `WriteService` 里返回 stub `WritingAIResponse`，还没有真正的模型调用路径。
- 当前客户端里仍然保留着 `Sources/VibeWriteApp/Shared/AI/WritingAIPromptBuilder.swift` 和 `Sources/VibeWriteApp/Shared/AI/RemoteWritingAIClient.swift`，但 backend 不能直接依赖 app target，所以本轮需要在 backend 自己落一套等价的执行路径。
- 这一张 task 只负责**backend 真实出字**，不做前端切换、不做 streaming / SSE 对外改造，也不做多模型。

## 本轮要做

- 在 `Backend/` 里新增 backend 侧的 AI 执行组件，用来：
  - 读取当前 `AdminSystemPromptStore` 的 snapshot
  - 读取当前 `AdminSecretStore` 的 provider API key
  - 读取当前 backend runtime 的 provider / model / metadata-route 配置
  - 组装与当前客户端语义一致的 system prompt / user prompt
  - 调用单一模型完成正文与 metadata 生成
- 把 `POST /v3/writes/start`、`POST /v3/writes/continue`、`POST /v3/writes/edit` 从 stub response 改成真实的后端 AI 执行路径
- 保持当前 route 名称、请求 DTO、响应 DTO 不变
- 保持 quota gate、request log store、device registry、后台登录和 system-prompt / secret config 行为不回退
- 让 backend 在测试环境里可以用 fake provider 走通，不要依赖真实 MiniMax 网络请求

## 建议实现内容

以下不是唯一实现方式，但请保持目标一致：

- `Backend/Sources/VibeWriteBackend/AI/BackendAIConfiguration.swift`
- `Backend/Sources/VibeWriteBackend/AI/BackendPromptComposer.swift`
- `Backend/Sources/VibeWriteBackend/AI/BackendAIProviderClient.swift`
- `Backend/Sources/VibeWriteBackend/AI/BackendAIExecutor.swift`
- `Backend/Sources/VibeWriteBackend/Writes/WriteService.swift`
- `Backend/Tests/VibeWriteBackendTests/BackendAIExecutorTests.swift`
- `Backend/Tests/VibeWriteBackendTests/WriteStartTests.swift`
- `Backend/Tests/VibeWriteBackendTests/WriteContinueTests.swift`
- `Backend/Tests/VibeWriteBackendTests/WriteEditTests.swift`
- backend 侧 prompt composer 必须是 backend-native 的，不要尝试 import app target 里的 `WritingAIPromptBuilder`
- prompt 语义要尽量贴合当前客户端行为：`templateBody` 负责共享基础提示词，`actionRulesJson` 负责按 action 的规则，`modelContextRulesJson` 负责 provider / model / metadata route 的规则
- backend runtime 里的 provider / model / metadata-route 配置可以继续沿用当前环境变量来源，和客户端当前 runtime 语义保持一致；provider API key 则从 `AdminSecretStore` 读取
- 测试里要用 fake provider 或等价替身，不能把真实 MiniMax 作为单元测试依赖
- `startDraft`、`continueWriting`、`edit` 都要走同一套 backend AI executor，但保留各自当前 action 语义
- `edit` 仍然必须保留选区校验和局部编辑语义
