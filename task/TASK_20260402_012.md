# TASK_20260402_012.md

## 本轮目标
本轮只完成一件事：继续清理 task011 后残留的 V1 讨论式入口和旧设计语义，把 VibeWrite 的正常 runtime 再往 V2-M1 的“编辑器优先”方向收紧一步。

这轮的重点不是再做新功能，而是修掉 task011 之后仍然存在的设计混乱点，确保页面骨架、入口文案、状态标签和真实交互都与 V2 文档一致。

具体来说，这一轮要解决的是：

- 首页不能再保留一个会把用户带进旧讨论壳的正常 runtime 入口
- `新建写作` 这类入口如果继续存在，必须与 V2 的单一直接起稿主路径一致，不能再创建独立的 blank discussion shell
- 正常 runtime 中不要继续显式暴露会让人联想到 V1 的讨论起稿语义
- 写作会话页继续保持正文中心、辅助层收起的方向，不要退回固定双栏工作台
- 页面效果要按 `docs/V2/UI2.0.md` 和 `docs/V2/Wireframes2.0.md` 的要求来重构和验收，而不是只修几个按钮文案

这轮的目标是把“看起来已经改了”变成“正常 runtime 里真的没有老设计残留”，同时不破坏现有 AI、patch、本地存储和回退链路。

---

## 本轮背景

- task011 已经把主界面收束到 V2-M1 的编辑器优先骨架。
- 但独立验证发现仍有一个 legacy affordance 没有彻底清掉：
  - 首页顶栏的 `新建写作` 仍然会打开一个 blank discussion shell
  - `WritingProjectMode.stageTitle` 仍然会在正常 runtime 中显示 `讨论起稿中`
- 这会让新旧设计语义混在一起，和 V2 要求的“单一直接起稿入口、正文优先、少入口、少模式切换”不完全一致。
- V2 的正式 UI 参考必须以以下文档为准：
  - `docs/V2/UI2.0.md`
  - `docs/V2/Wireframes2.0.md`
  - 以及对应的 `PRD2.0.md`、`IA2.0.md`、`AGENTS.md`、`Milestones.md`

### 这轮要统一的判断
- 首页是否真的只保留一个主起稿路径
- `新建写作` 在正常 runtime 里到底应不应该存在
- 如果保留，它是不是与直接起稿完全同义，而不是另一条入口
- `讨论起稿中` 这类状态是否还应该在正常 runtime 中出现
- 正常运行时是否还存在任何会让页面重新变得像 V1 的语义和视觉痕迹

## 本轮要做

- 先读文档，再改代码
  - 必须先阅读 `docs/V2/UI2.0.md`、`docs/V2/Wireframes2.0.md`、`docs/V2/PRD2.0.md`、`docs/V2/IA2.0.md`、`docs/V2/AGENTS.md`、`docs/V2/Milestones.md`

  - 不要只按代码层面修补，要按 UI 文档和线框图的页面结构去重构和验收

  - 首页正常 runtime 不能再出现一条独立的 blank discussion shell 路径
  - `新建写作` 如果保留，必须和 V2 的直接起稿主路径一致，或者改为更轻、更不抢戏的同义入口
  - 首页仍然要保留最近会话回流能力
  - 首页的空状态和占位文案要继续保持中性、空白、安静，不要像示例页

  - 正常 runtime 不要继续显式显示会让人联想到 V1 的 `讨论起稿中`
  - 如果需要显示阶段提示，尽量使用 V2 文档里的轻提示语义，例如 `起稿中`、`正文协作中`、`局部修改中`
  - 不要把讨论起稿当成首页主入口或主状态

- 保持写作页的 V2 骨架方向
  - 继续保持正文中心

- 真实验证页面效果
  - 改完后必须实际启动 app 看首页和会话页
  - 不能只看 `swift test` 或代码 diff
  - 必须确认正常 runtime 里没有明显的 V1 设计残留
  - 最好附上运行截图或等价的人工验证说明

- 维持现有闭环
  - 不改 AI 请求协议
  - 不改响应 JSON 契约
  - 不改局部 patch 机制
  - 不改本地项目存储结构
  - 不做多模型路由
  - 不做账号系统
