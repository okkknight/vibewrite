# TASK_20260402_016.md

## 本轮目标
本轮只完成一件事：把 V2-M4 做成“真实 AI + 短输出协议 + 流式输出”的完整主链路。

这轮的核心不是“能不能请求到 AI”，而是：

- 起稿 / 续写必须能在真实窗口里看到正文逐步增长
- 编辑必须仍然遵守局部 patch 语义，而不是回退成全文重写
- 输出契约必须短，`1024 token` 仍然是速度预算
- 流式输出必须是真流式，不允许只在最后一次性回填来假装支持 streaming

如果这一轮只做成一次性 `generateResponse`，或者只是把最后结果塞回正文，那就不算完成 V2-M4。

---

## 本轮背景

### V2 设计文档的共同要求
这轮必须同时参考：

- `docs/V2/PRD2.0.md`
- `docs/V2/IA2.0.md`
- `docs/V2/UI2.0.md`
- `docs/V2/Wireframes2.0.md`
- `docs/V2/Milestones.md`

这些文档对 V2-M4 的共同要求是：

- 接入真实 AI 请求
- 保持 `1024 token` 的速度预算
- 起稿和续写走短输出
- 编辑尽量走 patch 输出
- 真实 AI 不要把产品拉回聊天产品
- 正文仍然是页面主视觉，AI 只是周边增强层
- 流式输出是建议方向，而且不能流成一大坨 JSON

### 现在代码的真实状态
- 现在已有真实 AI client、请求构建、响应解析、友好错误映射和 1024 token 限制。
- 但当前 AI client 仍是一次性 request/response。
- 目前 app 层只知道“请求中 / 请求完成”，还不知道“正文正在边生成边显示”。
- 当前测试也主要验证一次性响应和错误映射，没有验证流式增量展示。

### 这轮要统一的判断
- 真实 AI 是否真的在流式返回正文增量
- 正文是否在响应完成前就能逐步显示
- 流式过程中 UI 是否仍然保持 V2 的正文中心气质
- 编辑是否仍然保持 patch 语义，而不是借着 streaming 退化成全文覆盖

## 本轮要做

- 把 AI 请求链路改成流式优先
  - 起稿和续写必须支持流式正文输出
  - 编辑可以选择流式 patch 文本，或者先流式收集内容再收口成 patch，但不能把一整个大 JSON 流式吐回来
  - 不允许把 streaming 只做成最后一次性回填

- 把流式正文真正接到 app 状态上
  - 正文在生成过程中就应该逐步更新
  - 生成未完成时，用户能在真实窗口里看到内容往前长
  - 不能只在最终完成后才刷新正文
  - 不能让正文在 streaming 期间空白等待

- 保持短输出协议和速度预算
  - `1024 token` 仍然是硬约束
  - prompt 必须继续鼓励短输出、可继续推进的正文
  - 不要把完整大纲、完整全文、完整长解释重新塞回输出契约
  - 不要因为 streaming 就放大输出体积

- 保持编辑仍然是 patch 语义
  - `edit` 不能因为 streaming 变成全文重写
  - 局部 patch、选区锁定、失败不污染正文这些 task015 的结论继续有效
  - streaming 只是在实现层提升体验，不是改变局部 patch 的边界

- 让 UI 体现“正在写”的真实过程，但仍然保持极简
  - 正文仍然是主视觉
  - AI 辅助层可以显示“正在写作”的轻量状态
  - 不要把 streaming 做成聊天窗口式的长消息流
  - 不要为了显示进度而增加控制台感组件

- 把 mock / 测试也改成流式语义
  - 不能只测最终结果
  - 必须能测到“先来一部分正文，再来后续正文，再完成”的增量过程
  - 必须能测到失败时正文不被污染
  - 必须能测到编辑仍然遵守局部 patch，不会因为流式而回到全文覆盖

---

## 本轮不要做

- 不做多模型路由
- 不做复杂调度器
- 不做大 JSON 全量正文流
- 不做新的聊天产品形态
- 不做工作台式双栏主界面
- 不做版本树
- 不做复杂 patch 编辑器
- 不把 streaming 退化成“等模型结束再统一回填”
- 不为了 streaming 去重写首页骨架或三动作主线

## 本轮主流程

1. 先阅读 `docs/V2/PRD2.0.md`、`docs/V2/IA2.0.md`、`docs/V2/UI2.0.md`、`docs/V2/Wireframes2.0.md`、`docs/V2/AGENTS.md`、`docs/V2/Milestones.md`，把“短输出 + 流式 + 正文中心”统一成这轮唯一目标。
2. 再阅读 `task/TASK_20260402_014.md`、`task/TASK_20260402_015.md` 和最新 handoff，确认 M3 的 patch 语义已经成立，M4 不能回退这些结论。
3. 找出现有 AI client 的真正写入点，确认它现在是不是仍然一次性 `data(for:)`，以及该在哪一层改成流式消费。
4. 把起稿和续写改成真流式正文输出，确保正文能在完成前逐步可见。
5. 让编辑路径保持 patch 语义，并在需要时以流式方式提升体验，但不能失去局部边界。
6. 把 mock AI、响应构建和测试一并改成流式语义，避免“真机是流式，测试还是一次性”的分裂。
7. 更新 unit test / UI test，覆盖流式增量、完成态、失败态和正文不污染。
8. 跑 `swift test` 和 `xcodebuild test -project VibeWrite.xcodeproj -scheme VibeWrite -destination 'platform=macOS'`。
9. 实际启动 app，确认正文在真实窗口里是逐步长出来的，而不是结束后才突然跳一下。

### 设计自由度
- 具体流式协议由 coder 自己决定，但必须是真流式，不接受“最后一次性回填”。
- 可以在 app 层使用最小的 stream event 抽象，也可以在 client 层包装成可消费的 async stream。
- 只要最终行为符合 `docs/V2/UI2.0.md` 和 `docs/V2/Wireframes2.0.md` 的正文中心原则，具体拆分可以由 coder 自己判断。
