# VibeWrite Roadmap 3.0

## 1. 这份文档的用途

这份文档只定义 V3 的整体推进计划，不拆到逐文件、逐接口、逐类的 task 卡片。

它回答的是：

- 先做什么
- 后做什么
- 每一阶段要达到什么门槛
- 哪些范围明确不做

后续每一阶段的 task 文档，会在这份 roadmap 确认后再单独拆分。

---

## 2. 固定前提

下面这些约定已经确认，不再在后续阶段反复改口：

- 后端不存文档正文
- 不做账号体系
- 后台只给单人使用，只需要一个简单登录
- `project.prompt` 保持为用户写作简述，继续保存在本地项目数据里，并随请求上传
- AI system prompt 配置完全后端化，但不做多版本管理
- 限额只按设备维度做日限额和周限额
- 统计单位固定为 AI 请求次数
- 被后端拒绝的请求不计数
- 离线时仍可作为普通文本编辑器使用
- AI 不可用时只提示网络不可用
- 日志只保留元数据，不保存正文和摘要
- 当前只接一个模型

---

## 3. 当前基线

这份 roadmap 不能只按历史文档推导，必须以当前代码为基线。当前仓库里已经能确认的事实是：

- 请求与返回的数据形状已经集中在 `Sources/VibeWriteApp/Shared/AI/WritingAIModels.swift`
- 客户端仍然在 `Sources/VibeWriteApp/Shared/AI/WritingAIPromptBuilder.swift` 和 `Sources/VibeWriteApp/Shared/AI/RemoteWritingAIClient.swift` 里直接做 prompt 和 provider 调用
- 本地合作态 metadata 仍然保存在 `Sources/VibeWriteApp/Shared/Documents/VibeWriteDocumentMetadataStore.swift`
- Markdown 正文和隐藏身份标记仍然是当前客户端的本地文档形态

所以 V3 的 roadmap 不是从零设想新产品，而是把现有本地写作壳子拆成可分发形态。

---

## 4. Roadmap 总览

V3 的推进顺序固定为 5 个阶段。

### 阶段 0：现状对齐与契约冻结

状态：已完成。

这一阶段不是开发阶段，而是前置冻结阶段。它的作用是把当前代码、V3 文档和迁移边界统一起来，给后续 task 文档提供唯一依据。

目标：

- 把当前代码、V3 文档和实际迁移边界对齐
- 冻结前端与后端之间的字段语义、错误类、路由命名和身份语义
- 明确哪些能力留在本地，哪些能力迁到后端，哪些能力进入后台

这一阶段的输出必须是文档和契约，不是代码实现。

必须产出的内容：

- 一份冻结后的请求与响应字段对照
- 一份冻结后的错误类与提示对照
- 一份冻结后的身份与限额口径说明
- 一份明确不纳入 V3 的范围清单
- 一份后续 task 文档可直接引用的边界说明

退出门槛：

- `project.prompt` 和后端 AI system prompt 配置的边界没有歧义
- 请求和响应字段可以一一映射到当前 Swift 模型
- 设备身份、限额统计、错误分类都没有未定口径
- 后续 task 文档可以直接按这些边界展开

备注：

- 这一步在当前规划里已经基本完成，所以 roadmap 里保留的是“冻结结果”，不是“待做开发项”

### 阶段 1：后端 AI 网关打底

目标：

- 先把后端服务搭起来
- 实现设备 bootstrap、设备令牌、设备限额、请求日志
- 接入单模型 provider adapter
- 把 AI system prompt 配置搬到后端
- 让后端能稳定流式返回正文和最终 metadata

这一阶段的重点是先让 AI 请求路径闭环，不碰文档云存储，也不碰账号体系。

依赖：

- 阶段 0 的边界冻结

退出门槛：

- 客户端可以通过后端拿到 AI 结果
- 客户端不再需要直连供应商 key
- 超限请求能被后端直接拒绝
- 后端不保存正文和摘要

### 阶段 2：前端切换到后端

目标：

- 把客户端的 AI 请求切到后端
- 保留本地编辑、保存、另存为、最近打开、离线编辑
- 把 `project.prompt` 作为本地写作简述继续带上请求
- 在客户端里去掉 provider key、prompt builder 和直接调用供应商的路径

这一阶段重点是让前端变成稳定的写作壳子，不再承担密钥和策略逻辑。

依赖：

- 阶段 1 的后端 AI 网关可用

退出门槛：

- 联网时 AI 请求全部走后端
- 离线时正文仍能编辑和保存
- AI 不可用时只提示网络不可用
- 客户端不再持有 provider key

### 阶段 3：单人后台管理页

目标：

- 做一个只给单人使用的极简后台
- 支持简单登录
- 支持密钥更新
- 支持 AI system prompt 配置查看和更新
- 支持额度查看和修改
- 支持请求和设备的查询

这一阶段不引入 RBAC、多账号、审批流或复杂报表。

依赖：

- 阶段 1 的后端管理接口

退出门槛：

- 后台能更新当前生效配置
- 后台能查看请求历史和设备状态
- 后台不展示正文原文和摘要原文

### 阶段 4：数据、留存和监控收口

目标：

- 固定数据库表结构和保留策略
- 固定请求日志只留元数据
- 固定正文和摘要不入库、不进日志
- 补齐监控、错误追踪、备份和审计

这一阶段是把实现收紧到可长期运行的状态，而不是继续扩功能。

依赖：

- 阶段 1 和 2 的请求链路已通
- 阶段 3 的管理入口已可用

退出门槛：

- 设备、请求、限额和配置的存储口径固定
- 留存策略与隐私边界一致
- 监控能够解释失败请求和限额拒绝

### 阶段 5：迁移切换与清理

目标：

- 删除客户端直连模型的正常路径
- 删除客户端密钥读取
- 删除客户端 AI system prompt 设计逻辑
- 删除旧 prompt builder 依赖
- 清理与 V3 决策冲突的旧说明和旧入口

这一阶段是上线前的收口阶段，重点是让默认路径只剩后端方案。

依赖：

- 前面四个阶段已完成并验证

退出门槛：

- 默认运行路径只走后端
- 旧的直接 provider 路径不再出现在正常构建里
- 文档、代码和后台入口都指向同一套 V3 方案

---

## 5. 明确不放进这份 roadmap 的内容

下面这些内容不会在 V3 里展开成正式路线：

- 云文档
- 账号体系
- 多模型平台
- 多租户
- RBAC
- prompt 多版本发布
- 文档库
- 作品集
- 项目管理

如果后面需要补充，只能作为单独决策，不允许悄悄混入当前 roadmap。

---

## 6. 这份 roadmap 和后续 task 文档的关系

roadmap 只负责回答“阶段顺序和门槛”。

后续 task 文档才负责回答：

- 每个阶段拆哪些具体任务
- 每个任务改哪些文件
- 每个任务怎么验收

也就是说：

- 先定 roadmap
- 再拆 task
- 不允许反过来
