# VibeWrite PRD 3.0

## 1. 产品名称

VibeWrite

## 2. 一句话定义

一个支持离线编辑、后端 AI 协作和简单后台管理的极简写作工具。

---

## 3. V3 阶段目标

V3 的目标不是把产品做复杂，而是把项目拆成可分发给别人使用的形态：

- 前端保留安静的正文编辑器和本地文件能力
- 后端接管 AI 能力、AI system prompt 配置、密钥、请求监控和限额控制
- 管理后台提供一个人可用的最简运维入口
- 用户在没有网络时仍然能够继续把它当作普通文本编辑器使用

---

## 4. 这版要解决什么

V2 时代，AI 逻辑、AI system prompt 配置设计和 provider 访问都在客户端里，适合自用，不适合分发。

V3 要解决的是：

- 不能把密钥和 AI system prompt 配置暴露在客户端
- 不能让每个客户端都直接连供应商
- 不能让限额、监控和错误处理分散在本地
- 不能让离线编辑能力依赖后端

---

## 5. 产品边界

### 5.1 要做的事

- 本地正文编辑
- 本地文件打开、保存、另存为
- 在线 AI 起稿、续写、局部编辑
- 后端统一管理 AI system prompt 配置和密钥
- 按设备维度做日限额和周限额
- 设备限额的统计单位固定为 AI 请求次数；每次被后端接受的 AI 请求计 1 次，拒绝请求不计数
- 后台查看请求记录
- 后台更新密钥和 AI system prompt 配置

### 5.2 不做的事

- 文档云存储
- 账号体系
- 团队协作
- 多模型接入
- AI system prompt 多版本发布系统
- 复杂审批和权限系统
- 文档库、作品集、项目管理

---

## 6. 已确认的默认决策

以下为当前 V3 的默认落地约定：

- 后端不存文档正文
- 不做账号体系
- 后台只做一个简单登录
- AI system prompt 配置完全后端化
- `project.prompt` 作为用户写作简述继续保留在本地项目数据中并随请求上传
- 不做 AI system prompt 多版本管理
- 限额按设备维度控制
- 限额类型只有日限额和周限额
- 限额统计单位固定为 AI 请求次数
- 每次被后端接受的 AI 请求计入日限额和周限额
- 被后端拒绝的请求不计入任何限额
- 超限直接拒绝，不做复杂降级
- 离线时仍保留普通编辑器能力
- AI 功能在离线时只提示网络不可用
- 日志只保留元数据，不保存正文和摘要
- 当前只接一个模型，不做多供应商

---

## 7. 目标用户

V3 的目标用户仍然是写作者，但使用方式更偏向分发：

- 想要一个简单、安静、能离线写字的桌面工具
- 想体验 AI 起稿和续写，但不想注册账号
- 目标用户接受轻量后台和简单配额限制

---

## 8. 典型使用流程

### 8.1 离线写作

1. 用户打开本地文件
2. 继续直接编辑正文
3. 保存到本地
4. 不访问后端也能完成普通写作

### 8.2 在线协作

1. 用户在输入框里发起起稿、续写或局部编辑
2. 客户端发送请求到后端 AI 网关
3. 后端检查设备限额
4. 后端拼装 AI system prompt 配置并调用单一模型
5. 客户端接收流式正文并刷新界面

### 8.3 离线调用 AI

1. 用户点击 AI 功能
2. 客户端发现网络不可用
3. 直接提示网络不可用
4. 不进入请求流程

---

## 9. 关键验收标准

- 未联网时仍可编辑和保存本地正文
- 未联网时 AI 功能明确提示网络不可用
- 客户端不再持有 AI 密钥
- AI system prompt 配置设计不在客户端二进制里
- `project.prompt` 作为用户输入仍保留在本地项目数据里
- 限额在服务端强制生效
- 超限请求被明确拒绝
- 后台必须能查看请求历史和状态
- 后台必须能更新密钥和 AI system prompt 配置
- 后端不保存正文和摘要
- 当前只需要支持单模型接入

---

## 10. 优先级

V3 的落地顺序为：

1. 先完成后端 AI 网关
2. 再完成设备限额
3. 再完成后台管理页
4. 最后补齐监控和体验优化
