# VibeWrite Deploy 3.0

## 1. 部署目标

V3 的部署目标是把后端 AI 网关和后台管理页放到阿里云上，并保持实现简单。

前端壳子是本地 macOS 应用，不部署到阿里云。

---

## 2. 最小部署形态

最小部署形态是：

- 一套后端应用
- 一套数据库
- 一套缓存
- 一套管理入口

阿里云组件固定为：

- `ECS` 跑后端 API 和后台页面
- `RDS PostgreSQL` 存配置、设备、请求元数据和会话
- `Redis` 存短期会话、限额计数和临时状态

说明：

- 文档正文不在云端存储
- 不需要对象存储来放正文
- 管理后台与 API 允许在同一后端服务里，用不同路由区分

---

## 3. 入口划分

固定保留两种做法：

### 3.1 单服务双路由

- `/api/*` 给客户端
- `/admin/*` 给后台

这是最省事的方式。

### 3.2 同域不同子域

- `api.xxx.com`
- `admin.xxx.com`

如果要清晰分边界，就拆分成独立服务。

---

## 4. 环境变量与运行配置

后端必须具备这些运行配置：

- 模型 provider key
- 当前模型名
- AI system prompt 配置来源
- 管理员登录凭证
- 数据库连接串
- Redis 连接串
- 会话密钥
- 时区
- 日 / 周限额默认值

前端必须具备：

- 后端 API 基地址
- 当前构建版本号

---

## 5. 密钥和配置管理

V3 的密钥和 AI system prompt 配置不得写死在客户端。

固定做法：

- 后端从受保护配置里读取密钥
- 管理后台修改受保护配置
- 修改后立即对新请求生效
- 不做多版本回滚系统，只保留当前生效值

---

## 6. 监控与日志

必须接入：

- 请求日志
- 错误日志
- 限额拒绝日志
- 后台配置变更审计

日志内容只保留元数据，不包含正文和摘要。

---

## 7. 发布顺序

发布顺序固定为：

1. 先上线后端 API
2. 再接前端客户端
3. 再上线后台管理
4. 再加请求监控和告警

这样先验证 AI 路径，再补管理能力。

---

## 8. 备份和恢复

需要备份的只有：

- 数据库
- 后端受保护配置
- 管理后台会话密钥或登录配置

不需要备份正文文件，因为正文不由后端保存。

---

## 9. 最小上线检查

上线前必须确认：

- 客户端能连到后端 API
- 后端能返回流式正文
- 后端能返回最终 metadata
- 限额生效
- 超限直接拒绝
- 后台登录可用
- 后台能改 AI system prompt 配置
- 后台能改密钥
- 前端离线编辑不受影响
