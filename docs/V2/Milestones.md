# VibeWrite V2 Milestones

## 总原则

V2 研发必须按“先体验骨架，再交互，再局部 patch，再真实 AI”的顺序推进。

不要反过来先做复杂 AI，再补 UI。  
不要先做很多入口，再去收束产品结构。

---

## V2-M1：编辑器优先的页面骨架

### 目标

把 VibeWrite 从工作台感页面，收束成“正文优先、安静、可持续写作”的页面骨架。

### 要做

1. 首页改成单一直接起稿页
2. 写作会话页改成正文中心结构
3. AI / 历史 / 版本都改为可收缩辅助层
4. 顶部栏只保留最轻入口
5. 空状态接近一张白纸

### 不做

- 不做完整 AI 能力
- 不做复杂版本树
- 不做模式墙
- 不做工作台式双栏主结构

### 验收标准

- 用户第一眼看到的是正文编辑器，不是控制台
- 首页只有一个明确的起稿入口
- 会话页正文永远是主视觉

---

## V2-M2：三动作主路径跑通

### 目标

把用户主路径收束成：

`startDraft -> continueWriting -> edit`

### 要做

1. 起稿动作跑通
2. 续写动作跑通
3. 编辑动作跑通
4. 让动作由当前状态和 UI 结构触发，而不是靠复杂规则分类
5. 保留简短协作反馈，但不把对话做成主舞台

### 不做

- 不恢复“先讨论再起稿”主入口
- 不重新引入扩写 / 缩写 / 润色按钮墙
- 不做多模式分流

### 验收标准

- 用户能从首页直接起稿
- 用户能在已有正文基础上续写
- 用户能对选区发起编辑
- 用户不会被迫在多个入口之间来回跳转

---

## V2-M3：局部 patch 与版本回退

### 目标

让编辑真正变成局部 patch，而不是全文重写。

### 要做

1. 选区编辑入口
2. 选区前后少量上下文切片
3. patch 应用机制
4. patch 期间锁定目标文本
5. 线性 revision history
6. 撤销 / 对比 / 重试入口

### 不做

- 不做重型版本树
- 不做复杂 patch 编辑器
- 不做长文全文替换作为常态

### 验收标准

- 长文本下也能保持局部编辑稳定
- patch 应用后正文局部变化清晰可控
- 用户可以随手回退或对比

---

## V2-M4：真实 AI 接入与短输出协议

### 目标

接入真实 AI，跑通起稿、续写、局部编辑的真实响应链路。

### 要做

1. 接入真实 AI 请求
2. 保持 `1024 token` 的速度预算
3. 起稿 / 续写走短输出
4. 编辑尽量走 patch 输出
5. 保持友好的错误映射
6. 保持协作反馈围绕正文推进

### 不做

- 不做复杂多模型路由
- 不做大 JSON 全量正文返回作为常态
- 不做无意义的语义规则堆叠

### 验收标准

- 起稿结果稳定、短、可继续推进
- 续写结果稳定、短、不中断体验
- 编辑结果能正确应用到正文局部
- 真实 AI 不会把 V2 拉回聊天产品

---

## V2-M5：体验打磨与细节收敛

### 目标

在主链路成立后，继续收敛体验细节。

### 要做

1. 更轻的空状态
2. 更自然的选区浮层
3. 更细腻的辅助层收起与展开
4. 更稳定的回退与对比体验
5. 更顺的输入与响应反馈

### 不做

- 不做与写作心流无关的功能堆叠
- 不做重型产品管理能力

### 验收标准

- 页面更像文本编辑器
- 智能能力存在，但不打扰
- 用户能持续写下去，而不是持续点按钮

---

## 统一执行要求

每个里程碑开始前，建议先输出：

1. 本阶段目标复述
2. 实现范围
3. 明确不做什么
4. 模块拆分
5. 实现顺序
6. 自测计划

每个里程碑结束后：

- 先独立 review
- 再更新 handoff
- 再进入下一阶段
